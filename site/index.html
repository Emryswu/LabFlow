实验室设备预约与故障工单平台

面向高校实验室：管台账、管预约、管报修。学生提交预约，教师审批，维修员处理故障，管理员看全局与审计。申请人一律取服务端登录用户。

能跑通的主流程

免费预约

选设备与时段后进入 PENDING。重叠的待审批可以同时存在。教师批准后才是 APPROVED，真正占住时段。超时未批变为 EXPIRED，用完后 COMPLETED。

计价预约

设备 hourlyPriceCents > 0 时，批准后进入 AWAITING_PAYMENT：占住时段，但支付窗口是 min(now + 支付窗口, startTime)，默认 10 分钟，不会越过开始时间。付清为 PAID。取消已支付预约时，仍有可退余额则进入 REFUNDING，到账后 CANCELLED。

报修

提交工单后，有权限的报修会取消冲突预约并让设备进入维护。管理员派单或维修员接单，处理、解决、关闭后设备恢复可预约。

四个角色

学生、教师、维修员、管理员。同一套界面按角色收窄导航。权限在服务端，不靠前端藏按钮。

仓库里已经落地的实现

模块实现
后端 Java 21、Spring Boot 3.5.16、Spring Security、JPA、Flyway。默认 H2；production 使用 MySQL、Redis、RabbitMQ。
前端 React 19.2、Next.js 16.2，由 vinext 构建。Node >=22.13.0。
预约锁 可在进程内公平锁与 Redis SET NX PX 之间切换，按 UTC 日期分片。数据库设备行锁仍是正确性底线。Redis 不可用时返回 503，不降级成无锁。
行锁顺序 状态变更固定 Equipment → Reservation，多行预约按主键排序，避免和报修路径形成 ABBA。
超时 RabbitMQ 固定阶梯 TTL 分桶加死信，数据库补偿扫描兜底。支付窗口复用同一套分桶。
支付 仓库内的模拟渠道，不接真实支付。幂等流水、出站重试、晚到账退款和差账工单。
认证 JWT 加 Refresh Token 轮换。登录限流可在本地与 Redis 之间切换，Redis 故障时限流失败关闭。

细节在 README 和 并发设计说明。创建路径的应用锁在事务外面：先用户锁，再按日期分片的设备锁，然后才开写事务。

已经合并到 main 的压测

下面的数字全部来自 benchmark/RESULTS.md（生成时间 2026-08-14T07:05:03Z）。原文声明表内数字没有改过，也没有估算。原始 JSON 和日志在 benchmark/results/ 与 benchmark/logs/。

环境

  • CPU：13th Gen Intel Core i9-13980HX，24 物理核 / 32 逻辑核，内存 31.63 GB
  • 系统：Windows 11 家庭中文版 10.0.26200
  • Java 25.0.2，压测客户端 Python 3.14.0
  • 一组是默认 profile：H2 内存库 + 进程内锁。另一组是 production：MySQL 8.4 + Redis 7.4。服务没有调大 Tomcat 线程或 Hikari 连接池。

正确性

同一设备、同一时段，N = 50 / 100 / 200，每档 3 轮。H2 与 MySQL + Redis 都是 9/9 轮恰好 1 个 HTTP 201，其余 409，0 失败。没有出现超过 1 个 201。

这是当时创建接口也把待审批重叠当成冲突时的结果。当前语义允许多条重叠 PENDING 并存，冲突发生在审批。所以这组「恰好一条 201」不能拿来判断现在的创建接口。

互不冲突时的整栈延迟

每个 worker 独占一台设备，各 500 个请求。这组比争用场景更接近「一次预约有多贵」，但两边仍是整套栈，不是只换锁。

报告自己的读法：未争用路径上 MySQL + Redis 大约 10 倍延迟、约十分之一吞吐。其中有跨进程数据库、Docker/WSL 网络和 Redis 往返，不能全部记在 Redis 锁上。

同一 MySQL 上只切换锁

这组已经合并。测量的代码是 a6684f3aa7eb7905c2a735201509f6e6b34e7cd5，报告在 benchmark/AB-RESULTS.md，原始文件在 benchmark/ab-results/20261128T161209Z/。同一台 MySQL 8.4.13、同一份库快照、同一个 JAR，只改 --labops.reservation-lock.mode。机器是 4 vCPU 的云虚拟机，内存 free -b 总计 16780623872 字节。没有为某一组改连接池或 Tomcat。

争用场景是 32 个学生预约同一台新设备。三轮两边都是 32 个 HTTP 201，没有 RESERVATION_LOCK_TIMEOUT。成功 P50：本地锁 241.345 / 238.243 / 243.291 ms，Redis 305.866 / 373.533 / 475.736 ms。

各自一台设备时，本地锁三轮都是 32/32，成功 P50 为 189.024 / 178.314 / 167.166 ms。Redis 第 2、3 轮是 32/32，P50 为 227.972 / 200.252 ms。第 1 轮 Redis 是 28 个 201 和 4 个 409 RESOURCE_BUSY，客户端记为无效，没有重跑。日志里这 4 次是 MySQL 死锁，不是 Redis 锁等待超时。18 次预热里有 17 次也有一次同样的死锁。

审批 6 轮都是恰好 1 个 HTTP 200 和 7 个 RESERVATION_CONFLICT。批准走数据库行锁，不走这层应用锁。
